## 1. 技术选型与理由

### 1.1 后端：Python 3.13 + FastAPI（推荐，而非 Node.js）

理由按重要性排序：

1. **中文文本相似度**：需求明确要求「jieba 分词 + TF-IDF/编辑距离加权，不用联网 API」。jieba 是 Python 生态独有的成熟方案（自定义词典、词性、关键词提取一应俱全）；Node 侧只有 nodejieba 等绑定，维护性差。
2. **计算核心的可测试性**：可靠性引擎是大量数值公式 + 因子组合 + 参数扫描。`numpy/scipy` 做敏感性扫描、曲线拟合、Weibull 分布（后续扩展）几乎零成本；`pytest` + `pytest.approx` 对浮点公式断言是最成熟的组合。
3. **BOM 导入导出**：`pandas + openpyxl` 处理 Excel 的合并单元格、隐藏行、脏数据类型（"0.1uF" 被 Excel 转成 "0.1"）最省事；报告导出 XLSX 也用它。
4. **纯函数计算库可 CLI 调用**：Python 单文件即可 `python -m core.cli ...`，无需构建产物，符合「计算核心与 Web 层解耦」。

Node.js 的优势（前后端同语言、类型贯通）在本项目收益有限：真正的工作量在领域公式和匹配算法，不在接口层。

**代价**：前后端两套语言。已通过 `OpenAPI → TypeScript 类型自动生成`（`openapi-typescript`）消除接口类型不同步的问题。

### 1.2 前端：React 18 + TypeScript + Vite + Ant Design 5 + ECharts 5

| 选择 | 理由 |
|---|---|
| React + TS | 生态最大，AI 生成代码质量最稳定；类型约束对 20+ 张表的数据结构很关键 |
| Ant Design 5 | 本系统重表格（BOM 明细、分类确认队列、降额违规清单、计算过程明细），AntD 的 `Table`（虚拟滚动/可编辑单元格/固定列）、`Steps`、`Tour`（新手引导）、`Tree`（分类体系）开箱即用，自研成本高 |
| ECharts 5 | Pareto 图（柱+累计折线双轴）、R(t) 曲线、敏感性曲线、雷达图全部原生支持；中文文档好 |
| Vite | 冷启动快，代理配置简单 |
| Zustand | 轻量状态管理，避免 Redux 样板代码 |
| react-hook-form + zod | 假设参数表单（含大量数值校验） |

### 1.3 数据库：SQLite → PostgreSQL

- 开发期 SQLite（`backend/data/reliability.db`），全部通过 SQLAlchemy 2.0 ORM + Alembic 迁移访问；
- **不用 SQLite 方言特有语法**（无 `JSON1` 依赖，JSON 字段统一存 `TEXT` + Pydantic 序列化；无 `AUTOINCREMENT` 依赖，用 ORM 主键）；
- 迁移 PostgreSQL 只需改 `DATABASE_URL` + 跑 `alembic upgrade head`。

### 1.4 报告导出

- **PDF**：`reportlab`（Platypus）后端生成。不用 `weasyprint`（Windows 需 GTK 运行时，装不上）。
- **XLSX**：`openpyxl` 多 Sheet（假设页 / 分类明细 / 计算明细 / Top 短板 / 磨损 / 降额 / 结论）。
- 报告文件名含 `engine_version` + `param_version`，保证可复现。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│  前端 React SPA (Vite)                                        │
│  项目列表 → BOM 导入 → 分类确认 → 假设参数 → 评估结果 →        │
│  磨损/降额 → 敏感性 → 报告 → 知识库维护 → 术语表/引导          │
└───────────────────────────┬──────────────────────────────────┘
                            │ REST /api/v1 (JWT)
┌───────────────────────────▼──────────────────────────────────┐
│  后端 FastAPI（Web 层，只做编排：取数 → 调 core → 落库）        │
│  routers/  services/  models(SQLAlchemy)  schemas(Pydantic)   │
└───────────────────────────┬──────────────────────────────────┘
                            │ 纯 Python 调用（无 DB、无 HTTP 依赖）
┌───────────────────────────▼──────────────────────────────────┐
│  core/  计算核心（纯函数库，可 pytest / CLI 独立运行）          │
│  ├ classify/     分类匹配引擎                                  │
│  ├ reliability/  失效率预计（Parts Count / Stress / RBD）      │
│  ├ wear/         磨损寿命模型                                  │
│  ├ derating/     降额判定                                      │
│  ├ sens/         敏感性扫描                                    │
│  └ standards/    参数库加载 + 公式元数据（标准来源标注）        │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只读
┌───────────────────────────▼──────────────────────────────────┐
│  参数库（JSON 种子文件 → 导入 DB，带版本号与来源引用）          │
│  params/mil217f_v1.json  params/telcordia_sr332_v1.json       │
│  params/derating_v1.json params/wear_v1.json  params/keywords  │
└──────────────────────────────────────────────────────────────┘
```

**关键约束（硬性）**：`core/` 里任何文件都不 import `fastapi` / `sqlalchemy`。它只接受 dataclass 入参（`PartInput`、`Assumption`、`ParamSet`），返回 dataclass 结果。Web 层负责把 ORM 对象翻译成 dataclass。

## 5. 计算核心设计

### 5.1 假设参数（四参数）与可选参数

| 参数 | 默认 | 取值 |
|---|---|---|
| `environment` | `GB` 地面固定 | `GB` 地面固定 / `GF` 地面移动 / `GM` 地面便携 / `MP` 车载 / `NS` 舰船 / `AIC` 机载有控 / `ARW` 机载无人 / `SF` 航天 / `C` 工业控制柜（Telcordia 侧映射 `GB/GF/GM/...`） |
| `ambient_temp_c` | 40 | 25–85，用于 π_T 与磨损 |
| `quality_level` | `commercial` | `commercial` / `industrial` / `automotive` / `military`（MIL-217 侧映射 π_Q 等级；Telcordia 侧映射 Quality 档） |
| `duty_cycle` | 1.0（或按「日通电 8h」= 0.333） | 0–1，λ 按通电占比折算，用于 R(t) 时间轴 |
| 冗余策略 | 全串联 | 按 `redundancy_group` 分组并联 |
| 目标 | 5 年 / 95% | |

### 5.2 零件计数法（Parts Count, MIL-HDBK-217F）

```
λ_equipment(FIT) = Σ_i  N_i × λ_g,i × π_Q,i
```
- `λ_g`：通用失效率，按「类别 × 环境」查表（MIL-217F 各 Section 的 Parts Count 表）；
- `π_Q`：质量因子，按质量等级查表；
- **不做温度修正**（这是 Parts Count 的定义：假设 40°C 典型条件，用于早期无详细应力信息阶段）。界面必须写清这一点，否则用户会以为调温度没反应是 bug。

### 5.3 零件应力法（Parts Stress）

```
λ_p(FIT) = λ_b × π_T × π_V × π_S × π_C × π_Q × π_E   （具体因子集合按类别由 factor_chain 声明）
```
- **π_T 两种模型**（不同标准/类别不同，故用 `formula` 字段区分）：
  - `power_law`：`π_T = ((T_op + 273) / T_ref)^n`，MIL-217 电容/电阻一类用此形式，`n` 按类别配置；
  - `arrhenius`：`π_T = exp( (Ea/k) × (1/T_ref − 1/T_op) )`，Telcordia 及部分器件用此形式，`Ea` 按类别配置，`k = 8.617333e-5 eV/K`。
- **π_V 电压应力因子**（例：电容 `π_V = (V_applied/V_rated)^m + 1`，`m` 按类别，指数形式在 JSON 里配）；
- **π_S 功率/电流应力因子**（电阻等）：`π_S = a × (P/P_rated)^b + c`，`a/b/c` 按类别；
- **π_E 环境因子**：查表；
- **工作温度 T_op 推算**：`T_op = T_ambient + ΔT_self_heating`，`ΔT` 由功率与热阻估算，无数据时用类别默认温升（如电阻 +5°C、功率器件 +20°C），**默认值必须在追溯明细里标为 `default`**。

### 5.4 Telcordia SR-332

- Method I（Parts Count）：`λ_SSI = λ_G × π_Q × π_S × π_T × π_E`，汇总后按 90% 置信度上限与**老化因子 π_CV（学习曲线，随累计工作时长下降）**修正；
- Method II/III（Parts Stress / 实验室数据）在参数库中预留结构，V1 实现 Method I + π_T Arrhenius + 早夭期修正；
- 界面与报告标注「Method I，90% 置信度上限」。

### 5.5 可靠性框图（RBD）与冗余

- 默认串联：`λ_sys = Σ λ_i`；
- 并联组（`redundancy_group` 相同的 k 个零件，或指定子系统）：先算组内 `R_g(t) = 1 − Π(1 − R_i(t))`，再折算等效失效率 `λ_g = −ln(R_g(t)) / t`（取评估时间点 `t = target_years × 8760 × duty`），代回串联；
- **必须提示**：并列冗余的收益前提是「共因失效可忽略」，界面上对此给一句警示（共因失效会让实际收益远低于理论值）。
- 结果同时给出「关闭冗余时的 MTBF」用于对比收益。

### 5.6 存活率与 MTBF

```
FIT_total = λ_sys（次/1e9 h）
MTBF(h)  = 1e9 / FIT_total
t_op(h)  = target_years × 8760 × duty_cycle
R(t)     = exp(− t_op / MTBF)
```
界面口径固定为：**「MTBF 理论值 + 目标年限存活率」，不出现「产品能用 X 年」的表述**；并在结果卡片固定展示免责声明（随机失效、数量级参考、需 RDT 验证）。

### 5.7 磨损寿命模型（模块五）

| 机制 | 公式（V1 采用形式） | 输入来源 | 缺数据策略 |
|---|---|---|---|
| 铝电解电容干涸 | `L = L0 × 2^((T_max_rated − T_op)/10) × K_V`，`K_V` 为电压降额修正（`V/V_r ≤ 0.8` 取 1.0，越高越小） | 从描述解析 `L0`（如 "10000h"）、`T_max`（如 "105℃"）、容值耐压 | 缺则用 `L0=2000h, T_max=105℃` 并标注 `default_conservative` |
| 风扇轴承 L10 | `L10 = L10_ref × 2^((T_ref − T_op)/10)`（润滑脂寿命每升 10°C 减半的工程近似） | 描述解析 `L10`（如 "L10 70000h @40℃"）、尺寸/转速 | 同上，`L10_ref=30000h@40℃` |
| 继电器触点 | `cycles = 电气寿命次数`（描述解析，如 "1×10^5 次"）；`years = cycles / (daily_ops × 365)` | 用户填日动作次数（默认 10 次/日） | 缺则 `1e5 次` |
| LED 光衰 L70 | `L70 = L70_ref × exp((Ea/k)(1/T_op − 1/T_ref))`，`Ea` 取 0.4–0.6eV（可配），`L70_ref` 取 LM-80 常见 25000h@85℃ 量级 | 描述解析光通维持率/结温 | 标注为「需 LM-80 实测数据，此处为工程估算」 |
| 连接器/开关 | `years = rated_cycles / (mate_per_day × 365)` | 描述解析插拔次数（如 "30 次"、"5000 cycles"） | 缺则按类别保守值 |

**整机结论合成**：
```
T_random(target R) = −ln(R_target) × MTBF / (8760 × duty)      # 由 MTBF 反推达标年限
T_wear             = min(所有磨损件 life_years)
T_system           = min(T_random, T_wear)
limiting_mechanism = "随机失效" | "磨损:<零件>:<机制>"
```
输出「磨损排行榜」（按 life_years 升序），与 MTBF 并排。

### 5.8 降额判定

```
ratio = applied / rated
ratio ≤ warn_ratio            → pass（满足）
warn_ratio < ratio ≤ max_ratio → marginal（接近）
max_ratio < ratio ≤ 1.0        → violation（超限，黄色→橙色）
ratio > 1.0                    → violation（超额定，红色）
解析不到 rated                  → no_data（缺数据，可人工补录）
```
阈值三级来自 `derating_rules`，默认值随标准表（如电容电压 ≤80%、电阻功率 ≤50%、稳压器功率 ≤70%）。**「接近」阈值取 `max_ratio − 0.1`**，是工程惯例的缓冲带，属自定规则，需在界面注明。

### 5.9 敏感性分析

- 扫描变量：`ambient_temp`（25→70，步长 5）、`quality_level`（枚举）、`duty_cycle`（0.2→1.0）；
- 每次扫描只重算受影响的因子（温度影响 π_T 与磨损，不影响 π_E/π_Q），避免 N 倍全量重算；
- 输出：曲线点集 + **弹性系数** `E = (ΔMTBF/MTBF) / (Δparam/param)`，并给出「哪个假设影响最大」的一句话结论；
- 附带 Pareto：各参数在 ±20% 扰动下对 MTBF 的影响幅度排序。

### 5.10 计算过程追溯（trace）

`core/reliability/trace.py` 在计算过程中产出结构化步骤数组，而不是拼字符串：

```json
[{"step":1,"name":"查基础失效率","formula":"λ_b = 表(MIL-217F, 铝电解电容, GB)","inputs":{"category":"CAP_ALU","env":"GB"},"value":0.012,"unit":"FIT","source":"MIL-HDBK-217F Notice 2, Sec.5.1 表"},
 {"step":2,"name":"温度因子","formula":"π_T = ((T+273)/313)^3","inputs":{"T_op":55.0,"n":3},"value":1.87,"unit":"-","source":"..."},
 {"step":3,"name":"质量因子","formula":"π_Q = 表(commercial)","inputs":{},"value":3.0,"unit":"-"},
 {"step":4,"name":"零件失效率","formula":"λ_p = λ_b × π_T × π_Q × π_E × qty","inputs":{...},"value":...,"unit":"FIT"}]
```
报告 PDF 里的「计算明细附录」与前端 `TraceDrawer` 共用这一份数据。

## 6. 分类匹配引擎

### 6.1 流水线

```
原始描述
  → ① 归一化：全角半角、大小写、单位统一（uF/μF/uf→uF；V/v→V；℃/C→°C）、
             数字与单位切分（"10KΩ"→{10, KΩ}）、去无意义词（"贴片""原装""ROHS"）
  → ② 分词：jieba（加载领域自定义词典，含"铝电解""X7R""NP0""L10""光耦"等）
  → ③ 特征抽取：封装(0402/0603/SOT-23/TO-220)、容值/阻值、耐压、精度、
             介质(X7R/NP0/Y5V)、温度等级(105℃)、位数(8bit)、通道数、品牌
  → ④ 打分（三个信号加权）：
       score = 0.50·S_kw + 0.30·S_tfidf + 0.20·S_char
         S_kw    : Σ(命中关键词权重) / Σ(该候选类目全关键词权重上限) ，负向命中直接扣减
         S_tfidf : 描述 vs 类目"文档"（name+aliases+description+种子描述样例）的 TF-IDF 余弦
         S_char  : 字符 3-gram Jaccard（对中文短描述比编辑距离稳，且抓得到"电解/陶瓷"这类关键词）
  → ⑤ 层级裁决：先判大类（cap/res/ic...），再在大类内判小类；
             大类置信度 <0.5 时直接进 unrecognized，不再往下判
  → ⑥ 分流：≥0.70 auto；0.30–0.70 pending_review（附 Top3 候选）；<0.30 unrecognized
```

**④′ 位号前缀加成（V1.1 新增，实现与设计稿的差异）**

BOM 里每一行都带位号（`R12` / `C3` / `U5` / `W2`），位号前缀是不含糊的品类证据：
描述写成"电容 0.1uF 50V 0603"时，到底陶瓷还是薄膜只能猜，但 `C3` 明确告诉引擎"这是电容"。
实现上把它当**第 4 个信号**，但不是加进加权公式（那会改动所有历史分数与阈值），
而是**对同大类候选加 0.10 分**，且只对已有分 ≥0.10 的候选生效：

```
score' = min(1, score + 0.10)   当且仅当 候选.parent == 位号推断出的大类 且 score ≥ 0.10
```

- 只能定**大类**，定不了小类——`C3` 不会告诉你它是陶瓷还是铝电解，所以它是加分项不是判决；
- 前缀匹配按长度优先（`LED3`→LED 而不是 L 电感，`PCB1`→PCB 而不是 P 连接器），顺序搞反会整批判错；
- 描述证据足够强时，位号给错也翻不了案（`M3×8 螺丝` 配 `W1` 仍判紧固件，已写成测试）。

### 6.2 为什么用这组权重

- 关键词是**领域强信号**（"铝电解"出现基本就定了），权重最高；
- TF-IDF 抓**上下文词共现**（"105℃ 2000h 低ESR" 更像电解电容），但对短描述不稳，故居中；
- 字符 n-gram 抓**拼写变体与错字**（"陶瓷电容"/"陶磁电容"），作为兜底，权重最低；
- 加权而非单一算法，正是为了在模拟数据的「高度相似」case（陶瓷 vs 薄膜 vs 铝电解都带"电容 50V 0.1uF"）上能靠关键词与介质特征分开。

### 6.3 刻意构造的边界 case（写入模拟器）

| 类型 | 示例描述 | 期望走向 |
|---|---|---|
| 高度相似但不同类 | `CAP CER 0.1uF 50V X7R 0603` vs `CAP FILM 0.1uF 50V ...` vs `CAP ALU 0.1uF 50V ...` | 三者分别正确归类（score>0.85） |
| 部分相似 | `电容 0.1uF 50V 0603`（缺介质） | pending_review，候选里陶瓷第一 |
| 完全不匹配 | `特殊定制件 图纸见附件` | unrecognized（整条没有任何品类信息） |
| 非电子件（V1.1 起可归类） | `定制五金支架 SUS304 折弯件` / `M3×8 十字圆头螺丝 不锈钢` | auto → 支架/钣金件、紧固件（早期版本只能判 unrecognized） |
| 描述过短 | `电阻 10K` | pending_review |
| 缩写/口语 | `10uF/16V 钽`、`贴片电阻 10K 1%` | auto（词典兜住） |
| 张冠李戴陷阱 | `电解电容 1000uF 25V`（实际是固态高分子） | pending_review，注释说明需人工定 |

### 6.4 知识库闭环（越用越准）

1. 人工确认 `final_category` ≠ `suggested_category` 时，写 `classify_feedback`；
2. `learn.py` 从「描述 − 已命中的该候选类目关键词 − 通用停用词」里提取 1–2 个**区别性片段**（如固态高分子案例里的"固态"），以 `weight=2, source=learned` 写入目标类目关键词，同时向原误判类目写一条 `is_negative` 排除词（权重 1）；
3. 同一片段被 ≥3 次独立确认后 `weight` 升到 3；被更正 ≥2 次后停用（`is_active=false`）；
4. 知识库页展示每个关键词的 `hit_count` 与来源，可手工禁用——**避免自动学习把库污染**。

- **元件目录** `sim/catalog.py`：18 大类 × 48 个标准类目，覆盖电容/电阻/半导体/IC/连接器/晶振/保险丝/继电器/开关/LED/模组/机电件，以及**结构五金件、线缆线束、导热辅料、包装标识**四类非电子件；描述按真实 BOM 写法生成（含单位、封装、公差、温度等级）。
- **料号一律真实**：电子件用厂商型号（`GRM188R71H104KA93D`），定制件用图号（`DWG-BRK-1042`），标准件用国标号（`GB/T818-M3×8-304`）。**不用自拟料号，也不给料号拼 `-01/-02` 后缀**——早期版本这么干，导出报告给同事看时第一反应是"这是假的吧"，而且和真实物料系统对不上。
- **规模即料号种类数**：料号不造假，所以行数受物料库限制（当前 74 种）；重复出现的同料号会被跳过而不是堆用量——曾试过"同料号用量相加"，结果一块板上出现 26 个 WiFi 模组、353 只电阻，MTBF 从百万小时掉到 20 万小时。
- **必注入的边界 case**：见 §6.3（6 类共约 12 条）；
- **预置问题零件**（用于演示异常预警）：
  1. 铝电解电容 `1000uF/25V` 工作在 60°C、电压应力 0.92 → 降额 violation + 磨损寿命最短；
  2. 风扇 `L10 30000h@40℃` 实际 55°C → 磨损限制项；
  3. 继电器 `1e5 次` 日动作 200 次 → 仅 1.4 年；
  4. 一颗国产二三极管质量等级 low → π_Q 拉高，进入短板 Top3；
  5. 一条描述完全不可识别（`定制支架 SUS304`）；
  6. 重复料号（同一料号两行）+ 缺 `qty` 列的一条（校验演示）。
- **两套可比 BOM**：`方案A（基准）` 与 `方案B（换料+加冗余）`，用于演示方案对比与冗余收益。

## 14. 实现说明：与设计的差异、踩过的坑（V1.0 交付时补记）

设计稿已按确认执行，以下是实现阶段不得不偏离或补充的地方，逐条说明原因，便于后续维护者判断"这是妥协还是错误"。

### 14.1 与设计稿的差异

| 项 | 设计稿 | 实现 | 原因 |
|---|---|---|---|
| 前端状态管理 | Zustand | 未引入，用 props + 局部 state | 8 个 Tab 的上下文只有"当前项目/版本/评估 id"三个值，由 `Workspace.tsx` 单点持有即可；引入全局 store 反而增加"哪个状态是真的"的排查成本 |
| 表单校验 | react-hook-form + zod | antd `Form` + 后端 Pydantic 双保险 | 前端只做"必填/范围"这类提示，真正的边界（如 duty∈(0,1]、存活率<1）由后端 `_check_assumption` 统一裁决，避免两处规则漂移 |
| 接口类型 | openapi-typescript 自动生成 | 手写 `api/index.ts`（只覆盖页面真正读的字段） | 生成类型对 20+ 张嵌套表会产生大量噪音类型；内部应用用"少数关键字段 + `any` 兜底"更省维护 |
| 数据库迁移 | Alembic | `Base.metadata.create_all` | 交付物要"三步启动"，多一步 `alembic upgrade` 就是多一个卡点。改用 PostgreSQL 生产部署时再引入 Alembic（表结构已集中在一个 `models.py`，切分不难） |
| 大类编码 | `XTAL`/`FUSE`/`RELAY`/`SWITCH`/`LED` | 改为 `XTAL_G`/`FUSE_G`/… （`_G` = group） | 同名编码同时被大类与小类占用，触发 `UNIQUE constraint failed: categories.code`。加后缀后大类/小类编码空间分离，`parent_code` 指向明确 |

### 14.2 实现阶段发现并修复的问题

1. **模拟 BOM 的用量串行**：变体分支漏了 `qty = item["qty"]`，导致上一行（320 个焊点）的用量被带进电解电容，
   造出"501 只电解电容"这种数据，整机 MTBF 从 60 万小时掉到 3.6 万小时、判定从 PASS 变 FAIL。
   这类"变量跨迭代残留"不会报错，只会让演示数据看起来荒谬——已加注释固化。
2. **变体应力配错**：早期按固定比例（0.7/0.65/0.55）推工作应力，而各类目的降额上限不同（电阻功率 0.5、电感电流 0.6），
   于是凭空出现 30+ 条"降额超限"，把真正的 4 条问题行淹没。改为**沿用基准行的应力/额定比值**。
3. **降额浮点边界**：`2.1 / 3.0 = 0.7000000000000001`，与上限 0.7 比较被判"超限"，实际含义是"正好卡在上限"。
   比值判定统一加 `EPS = 1e-9` 容差。
4. **温度漏解析**：`105度`（国内常见写法）解析不出来，导致电解电容"额定最高温度缺失"，磨损与降额双双退化为
   `no_data`/默认值。`parse_temp_max` 增加"度"的写法。
5. **连接器磨损默认值不合理**：板对板连接器按"0.05 次/日"算，30 次额定寿命 → 1.6 年，会莫名其妙成为整机短板。
   改为 0.002 次/日（装配一次 + 偶尔维护），并在 `wear_v1.json` 的 `notes.daily_ops` 里写明"这类输入对结果极敏感，
   属关键假设，必须由使用场景给出"。
6. **计数法的温度敏感性**：MIL 计数法不含 π_T，温度扫描是一条平线。这在数学上正确，但用户会误读为"温度不重要"。
   敏感性页与结论文案改为显式说明"当前口径里没有这一项，要看向应力法/Telcordia"。
7. **磨损限制项上升为预警**：PASS/FAIL 只看随机失效。若磨损视角短于目标年限，现在会在结果预警区强制出现一条
   "MTBF 达标 ≠ 寿命达标"，避免评审只看绿色的 PASS 就签字。

### 14.3 演示数据的实测指标（默认假设：GB / 40°C / 商用级 / 8h 每日 / 5 年 95% / MIL 计数法）

| 指标 | 值 | 说明 |
|---|---|---|
| BOM 行数 | 76 | 14 条边界 case + 62 种真实料号（含 7 类非电子件）；不再靠伪造料号铺量 |
| 自动归类率 | 93.4% | 71 行自动；4 行待确认（"三兄弟 0.1uF 50V"这类必须人判）+ 1 行未识别（`特殊定制件 图纸见附件`） |
| 总失效率 / MTBF | 425.9 FIT / 235 万小时 | 判定 PASS，5 年存活率 99.4% |
| 非标准覆盖件 | 10 行 / 30 件 / 7 类，合计 34.2 FIT | 结构五金、线缆、导热、包材；占整机 λ 的 8%，报告单列并注明"不可作为定稿依据" |
| 磨损限制项 | 继电器触点 4.57 年 | 随机视角远高于此 → 整机取 4.57 年，**低于 5 年目标**，正是"MTBF≠寿命"的现场案例 |
| 降额 | 37 满足 / 7 接近 / 3 超限 / 20 缺数据 | 超限项集中在 92% 电压的电解电容、95% 负载的电源模块 |
| 双标准比 | MIL 425.9 / Telcordia 226.4 = 1.88 | 与"保守估计 vs 现场数据"的常见差距一致 |

> 上述数字随参数库与知识库改动会变化，属于预期行为；同一份评估记录内的数字不会变（快照 + param_version）。

### 14.4 部署形态的调整：从"两端口"到"单端口"

设计稿写的是「前后端分离，前端由静态服务器托管，`/api` 反向代理到后端」。这在生产环境没问题，
但交付时发现它对"把系统搬到另一台机器上给人用"很不友好：要么装 nginx，要么记住两个端口，
要么改 CORS 白名单。对一台没有运维的内网机器，这三步里任何一步都可能卡住。

最后的做法是让后端**自己托管前端构建产物**（`app/main.py` 末尾），逻辑是"有就托管、没有就跳过"：

| 状态 | 行为 |
| --- | --- |
| 存在 `frontend/dist/index.html` | 挂 `/assets` 静态目录 + 通配路由回退到 `index.html`（支持前端路由深链接刷新） |
| 不存在 | 跳过，`GET /` 返回一段 JSON 提示，不影响 `npm run dev` 的开发模式 |

两个容易踩的细节：

1. **未命中的 API 路径必须返回 404 JSON，不能回退到 index.html**。否则前端 `fetch` 会拿到一段 HTML，
   报出 `Unexpected token <` —— 比 404 难查十倍。
2. **`/assets` 用 `StaticFiles` 挂载而不是走通配路由**。静态文件由 Starlette 处理，能带 `ETag` 与
   `304 Not Modified`（实测二次加载时 antd/echarts 两个大 chunk 都是 304，省掉约 2MB 流量）。

配套改动：
- `Settings.cors_origins` 支持 `CORS_ORIGINS` 环境变量（逗号分隔）。同源部署下不需要动它。
- 新增 `tools/pack.py` + `pack.bat`：生成不含 `.venv` / `node_modules` 的发布包
  （约 1 MB；带离线依赖约 38 MB）。

### 14.5 一键启动脚本踩的两个坑（Windows 批处理）

1. **批处理文件不能存成 UTF-8**。命令解释器按字节读脚本，UTF-8 的中文会被从中间切断，
   剩下的半截字节被当成命令执行，报 `'xx' is not recognized`。实测里被切的是某行 `echo` 的中文，
   脚本仍能跑完（错误只是噪音），但用户会以为坏了。改成 **GBK（cp936）+ `chcp 936`** 后彻底消失。
2. **`timeout` 不能写裸命令名**。机器上装了 Git for Windows / MSYS2 时，PATH 里的 `timeout`
   是 coreutils 版本，参数是 GNU 风格，收到 `/t 4` 会报 `invalid time interval '/t'`。
   改用绝对路径 `%SystemRoot%\System32\timeout.exe /t 4 /nobreak`。

另外脚本刻意做了三件事，都是为了让"双击"这件事在别人的机器上也能成立：
- **端口顺延**（8000 被占就试 8001…8010）。否则窗口闪一下就没了，用户完全不知道发生了什么。
- **依赖自检用 `import` 而不是逐个 `pip show`**，快且不会误判。
- **延迟 4 秒再开浏览器**。服务还没监听端口就打开会是白屏，而白屏会被当成"启动失败"。

### 14.6 离线安装的坑：sdist 与 setuptools

`pack.py --with-wheels` 第一版只是 `pip download -r requirements.txt`，结果 `jieba` 存成了 `.tar.gz`。
在无网机器上装时报：

```
ERROR: Could not find a version that satisfies the requirement setuptools>=40.8.0 (from versions: none)
```

原因是 **Python 3.12 起 `venv` 默认不再安装 setuptools**，而 sdist（源码包）安装必须先构建。
解决办法是在**有网的打包机上**用 `pip wheel` 把 sdist 预编译成 whl，再额外带上 `setuptools` / `wheel` 兜底。
目标机器于是只解压、不编译 —— 这条路径在干净目录 + 断网环境下实测通过。

### 14.7 "Failed to fetch" 事件：错误信息也是产品的一部分

交付后收到的第一个反馈不是功能问题，是"打开之后是 fail to fetch，点哪个都是"。
复现后确认：**页面本身没问题，是服务进程被关掉了**（开发调试结束时清了后台任务），
而浏览器里那个标签页还开着，于是点任何按钮，`fetch` 都连不上后端。

这里有三层问题，只有第一层是"偶发"的：

| 层次 | 现象 | 处理 |
| --- | --- | --- |
| 服务没了 | 页面能点，请求全挂 | 使用者关掉黑窗口是常态，无法阻止；只能让他**知道**发生了什么 |
| 错误无法自解释 | 浏览器只给一句英文 `Failed to fetch`，不含任何原因 | 在 `api/client.ts` 统一捕获网络层异常，翻译成中文并给出下一步动作 |
| 没有全局状态 | 只有点了按钮才知道断线，且提示 3 秒后消失 | 新增常驻的 `BackendStatus` 横幅：定时 ping `/api/health`，断开时常驻显示 + 手动「重新检测」 |

#### 为什么网络层错误必须单独包一层

`fetch` 只在"请求根本没发出去"时抛异常（连接被拒、断网、`file://` 协议、被安全软件拦截），
而这时它给的文案恒为 `Failed to fetch`，不告诉你属于哪一种。这四种情况的处置动作完全不同：
重启服务 / 改端口 / 别双击 HTML / 检查网络。所以 `client.ts` 里的 `send()` 把异常统一转成
`ApiError(msg, NETWORK_ERROR)`，`status = 0` 让调用方能和业务错误区分开。

toast 只放一句话（一行能读完）；三条排查步骤放在横幅的 Tooltip 里 —— **同一个信息在两种载体上要有不同详略**，
否则 toast 变成三行小字，反而没人看。

#### 顺带修掉的两个坑

1. **`start.bat` 固定 `timeout 4` 后开浏览器**。这只有在"依赖已装好、数据库已建"的机器上成立。
   首次运行要装 30 多个包，可能超过一分钟，那 4 秒过去端口还没监听，浏览器显示
   "无法访问此网站" —— 使用者第一反应就是"这东西坏了"。
   改为 `tools/wait_and_open.py` 轮询 TCP 连接，连上才开；180 秒还没通则**不开**，
   让控制台里的真实报错露出来，而不是用一个白屏页盖住它。

2. **内联脚本里的 `</head>` 会把构建产物撕碎**。为了拦住"双击 index.html"这种操作，
   我在 `frontend/index.html` 里写了一段检测 `location.protocol === 'file:'` 的内联脚本，
   用 `document.write` 输出一整页中文说明。结果 Vite 构建时把 `<script src>` 和 `<link>`
   注入到"第一个 `</head>` 之前"—— 而这个 `</head>` 出现在我的**字符串字面量**里
   （后来甚至只是出现在**注释**里也照样中招）。字符被从中间切断，注入的 `<script>` 的
   闭合标签又提前终止了外层脚本，页面上直接印出 `' + '' + ' ' + '` 这种碎片。
   修法：字符串与注释里都不出现 head/body 的结束标签字面量，改用 DOM API 逐节点构造提示页。

### 14.8 V1.1：把「非电子件」接进分类体系（以及三处连带修正）

起因是一张截图：BOM 里 `定制五金支架 SUS304 折弯件`、`M3×8 十字圆头螺丝 不锈钢` 两行判成「未识别」，
下拉框还预填了 `存储器（4）` 和 `MOSFET（1）`——4% / 1% 的猜测被当成"系统建议"摆在那里。

**根因有三层，只补关键词是治不好的：**

1. **分类库真的没有这些品类**。18 个类目的第一版只有 14 个电子大类（电容/电阻/半导体/IC/连接器/晶振/
   保险丝/继电器/开关/LED/模组/机电件），`EM 机电件` 底下也只有风扇、PCB、焊点。
2. **参数库没有对应的 λ**。分类库加词很容易，但每个类目必须在 MIL-217F 与 SR-332 两套参数里都有
   `family` 与 `lambda_g`，否则一点「评估」就抛"分类在参数库中不存在"。只改分类库，等于把报错从
   "未识别"推迟到"评估失败"。
3. **界面把低分猜测当建议预填**。`candidates[0]` 无条件填进下拉框，1% 的分也照样显示成 `★ MOSFET（1）`，
   用户顺手点确认就把错的分类确认掉了——比不预填危险得多。

**做法：**

- 新增 4 个大类、11 个小类：结构五金件（支架/紧固件/外壳/绝缘件）、线缆线束（导线/线束/扎带）、
  导热辅料（导热垫/胶粘剂）、包装标识（包装/标签），关键词从 250 扩到 357。
- 两套参数库同步新增 `mechanical` 因子族与 11 条类目。机械件人为**留空 `parts_stress`**——
  它们没有结温、没有电应力，硬套 Arrhenius 会得到一个没有物理意义的乘数。
- 参考业界做法（Relyence 等工具把 MIL-217 与 **NSWC-11 机械件标准 / NPRD 非电子件数据**拼着用），
  本系统不假装有标准模型，而是显式标注：`is_standard=false`，λ 取 0.01~2 FIT/件（压接点最高、
  螺丝最低），结果页与报告里单列一条告警。**静默跳过是绝对不行的**——那会让 MTBF 凭空变好。
- Telcordia 计数法对这类零件跳过 π_T（新增 `pi_T_exempt`），并在追溯里留一条 `π_T = 1.0（无温度模型）`，
  避免用户以为是漏算。

**连带修的三处：**

| 问题 | 现象 | 修法 |
| --- | --- | --- |
| 演示数据造假料号 | `SIM-CAP-CER-100N50`、变体 `-01/-02` 后缀；导出报告被人质疑"这是假的吧" | 换成真实型号 / 图号 / 国标号；规模放大时不再编料号，料号用尽就停 |
| 同料号堆用量 | 改成"同料号并到一行累加"后又走到另一个极端：单板 26 个 WiFi 模组、353 只电阻，MTBF 从 235 万掉到 22 万 | 重复料号直接跳过，行数 = 料号种类数（74 种），用量保持物理合理 |
| 分类只看描述 | `电容 0.1uF 50V 0603` 这类描述天生分不出介质，永远只能进人工队列 | 加入位号前缀第 4 信号（见 §6 ④′），`电阻 10K` + `R1` 从 37% 提到 77% 直接自动归类 |

**验证**：pytest 44 项全过（新增 4 项：非电子件不被跳过、11 个新类目在两套标准中都存在、
Telcordia 跳过 π_T、位号只影响大类不影响结论）；浏览器实测——`M3×8 螺丝` 判紧固件（100%）、
支架判 100%、线束 84%，未识别行的下拉框回到「选择类目」空态。

### 14.9 V1.2：把「限制」做成系统能力，而不是文档里的一段话

起因是一句追问：**「我不卖，就部门内部用，但要把限制讲清楚。」**

原来系统对限制的表达只有两处：参数库里的 `disclaimer` 文本，和报告附录 C 六条写死的免责。
两者都是"通用免责"，读者会整段跳过，而且说不清这一次评估到底有多少零件用了默认温升、
非电子件占了多少 FIT。**限制讲不清，等于没讲。**

#### 一、参数库自报「数据成色」

四个数值参数库（MIL / SR-332 / 磨损 / 降额）新增两个字段：

| 字段 | 值 | 含义 |
|---|---|---|
| `data_quality` | `demo` / `partial` / `verified` | 全部是公开文献量级 / 部分类目照表录入 / 全部照表录入 |
| `data_quality_note` | 文本 | 当前状态的说明 + 怎么改到 `verified` |

`ParamSet` 带上这两个字段，`param_meta` 透出给 Web 层，界面在三个位置显示：

- 参数库页：详情标题旁一个彩色标签（红=示例量级 / 橙=部分 / 绿=已录入）
- 结果页：「读数字前先看」折叠面板的第一条
- 报告：附录 B 的「数据质量」行 + 附录 C 第一条

**为什么值得单开一个字段**：算法算得对是一回事，喂进去的数字可不可信是另一回事。
两者在界面上长得一样，用户就会默认结果是照标准算的。

#### 二、报告附录 C 从静态免责改成动态清单

`report.py` 新增 `_limitations(payload, param_meta)`，按本次结果现算七项：

| 维度 | 数据来源 | 缺了会怎样 |
|---|---|---|
| 参数基准值 | `param_meta.data_quality` | 所有数字的成色 |
| 非电子件（标准未覆盖） | `parts[].is_standard == false` 的行数/件数/FIT/占比 | 这部分 FIT 不是标准值 |
| 默认温升/应力 | `trace[].is_default` 涉及多少个零件 | 温度因子可能偏乐观 |
| 置信度口径 | `confidence_factor_90 == 1.0` | 报的是中值不是 UCL |
| 冗余模型 | `assessment.redundancy` 非空 | 收益是上限 |
| 降额缺数据 | `derating.items[].verdict == no_data` | 「未判定」被误读成「合格」 |
| 磨损输入 | `wear.items[].using_defaults` | 寿命按保守默认值 |

每条都带「本次情况」和「对结论的影响」两列。表后接三块文字：
**可以直接用于**（横向比较、短板排序、降额初筛、数量级判断）、
**不能用于**（对外报告、认证、索赔、跨标准引用）、**口径提醒**（数倍偏差、不替代 RDT、MTBF≠寿命）。

XLSX 报告同步新增「局限性」工作表，位置紧跟「汇总」——让人先看边界再往下看数字。

#### 三、参数录入工单：`tools/param_worksheet.py`

把"拿标准原表替换示例值"变成可交付的流程：

```
export  → Excel 工单（五张表：说明 / λ_b / π_E / π_Q / π_T）
import  → 校验，不改文件
import --apply → 校验通过后写回 JSON（自动备份 .bak + 自动升 data_quality）
```

设计上的几个决定：

- **只给章节名称，不给编号**。编号在不同 Notice / Issue 之间会挪，写错反而误导。
- **留空 = 不动**，不是填 0。覆盖率按填了几格算，全填才升 `verified`。
- **能查的限度**：数值合法性、量级（>1e6 或 <1e-6 FIT 大概率是单位错）、π_E/π_Q 单调性
  （抄错行最常见的形态就是两个值换了位置）。**查不了的**：抄错列、抄错标准版本、漏类目。
  所以文档里明确写了「建议两个人各填一份交叉核对」——这一步没有捷径。
- **回写保留原文件缩进**（`_detect_indent`），否则整个 JSON 的 diff 会炸开，评审时看不出改了什么。

#### 四、顺手修掉一个真 bug：存活率被存成百分数

做浏览器验证时发现的：主页项目卡片显示「目标：5 年存活率 ≥ 9500%」。

根因是同一个数在系统里有两套写法——数据库与计算核心用小数（`0.95`），项目表单让用户按
百分数填（`95`），而 `onCreate` 直接把表单值提交了，没有转换。后果比显示难看严重得多：

- 卡片 `pct(95, 0)` → 「9500%」
- 评估时把 95 当目标 R(t)，**判定永远不通过**
- 整个过程不报任何异常，只会让人以为"产品可靠性不够"

修法两头都做：前端提交时 `/100`（正规），后端 `ProjectCreate/Update` 加
`field_validator`（>1 视为百分数自动归一，`≤0 / ≥1` 抛 422）。加这条兜底是为了
API 直调的人——他们会顺手传 95，与其 422 拒绝，不如按常识解释掉。

同时重建了演示数据（旧的 `target_survival=95` 是脏数据）。

#### 验证

- pytest **46 项全过**（新增 2 项：存活率 95→0.95 且非法值被拒；参数库必须自报数据成色）
- 浏览器实测（`frontend/scripts/check_limits.mjs`）：结果页出现「读数字前先看」，
  展开后 5 条与后端算的一致；参数库页标签正确；零控制台错误
- 工单工具跑通三条路径：正常填 → 校验通过；非法值 + π_E 乱序 → 拦下；`--apply` → 写回并升 `partial`，备份可回退
- 报告重新生成：PDF 274 KB / XLSX 21 KB，附录 C 显示 5 条实算局限
