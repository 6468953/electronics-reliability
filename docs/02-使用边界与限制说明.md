# 使用边界与限制说明

> 面向：使用本系统做可靠性预计的部门同事
> 版本：v1.1 ｜ 对应系统版本 1.1.0
> 结论先行：**这是设计阶段的内部估算工具，不是交付工具。** 它能替代的是部门里那张传了三手的 Excel，不能替代客户认可的 MTBF 报告。

---

## 一、五条红线

以下场景不要用本系统的数字，用了会出事：

| # | 不能用于 | 原因 |
|---|---|---|
| 1 | **向客户正式提交的 MTBF 报告** | λ 基准值是示例量级（见 §2.1），不是标准原表；质量等级做过映射（§2.2） |
| 2 | **安全 / 认证相关论证** | 功能安全（ISO 26262、IEC 61508）、UL/CE、医疗器械注册，都需要可追溯的认可方法与第三方数据，本系统不满足 |
| 3 | **索赔、召回、寿命承诺的判定依据** | 单点估计，无置信区间、无统计推断，经不起法务层面的推敲 |
| 4 | **跨标准交叉引用** | MIL-217F 与 SR-332 的 λ_G 建模口径不同，两个数字不能互相代入、不能相加（§3.2） |
| 5 | **拿演示项目的数据当结论** | `演示项目 · 智能网关 GW-200` 是程序生成的模拟 BOM，只用于展示功能 |

判断标准很简单：**这个数字最终会不会出现在有外部单位签字的地方？** 会，就不能用。

## 二、数据层面的限制

系统的每一处参数缺口都写在 `backend/params/*.json` 的 `disclaimer` 字段里，界面上也能看到。这里汇总成人话。

### 2.1 λ 基准值（最大的一条）

两套标准的获取成本完全不同，必须先分清：

| 标准 | 获取成本 | 说明 |
|---|---|---|
| MIL-HDBK-217F Notice 2 | **免费** | 美国国防部公开文件。在 `quicksearch.dla.mil` 搜 `MIL-HDBK-217F`，下载 Revision F + Change Notice 1 + Change Notice 2 三份 PDF 拼合，无需注册、无授权限制 |
| Telcordia SR-332 Issue 4 | **付费，且带授权限制** | Ericsson（Telcordia）按 Enterprise License 销售，官网只受理「报价申请」，不公开价格。正文首页明确：仅限 EL 被许可方之间共享，禁止转发、下载、转售 |
| GJB/Z 299C、GJB/Z 35-93 | 受控采购 | 走国内标准发行渠道购买，不在公开网络 |

系统当前状态：

| 项 | 现状 |
|---|---|
| 是什么 | MIL-217F 的 λ_b、SR-332 的 λ_G，以及 π_T / π_Q / π_E 各自的档位 |
| 现状 | **两套都是近似值，没有照表录入**：λ 取公开文献、教材、厂商 FAQ 中反复引用的典型量级；因子档位按标准的公开描述构造 |
| MIL-217F 侧的定性 | **属于「能抄没抄」**。这是免费公开文件，实现时按「演示够用」的标准跳过了逐表录入 —— 是欠账，不是权限问题 |
| SR-332 侧的定性 | **属于「拿不到」**。没有 EL 授权就没有合法副本，只能近似 |
| 影响方向 | 无法确定：可能整体偏低（现代器件实际失效率普遍低于老标准），也可能某个类别偏高 |
| 后果 | 绝对值不可引用；同一套参数下的**相对比较**仍然成立（见 §4） |
| 怎么消除 | MIL-217F：下载官方 PDF，把各器件章节的 base failure rate 表、π_T 曲线、π_E（14 档）、π_Q 档位录进 JSON。**零成本，约 1~2 人日**；SR-332：先采购 EL，再录 Section 8/9 |

> 关于「网上能搜到 SR-332 的 PDF 能不能用」：能搜到，但正文带 Enterprise License 水印与授权声明，
> 公司用途使用属侵权，不建议。要么走采购，要么只报 MIL-217F。

### 2.2 质量等级的映射

SR-332 原本只有 Quality Level **I / II / III** 三档，本系统借用了 MIL-217 的四档命名（商用 / 工业 / 车规 / 军品）去映射。

| 影响 | 说明 |
|---|---|
| 方向 | 不确定。若客户规格指定的是 SR-332 Level II，而界面选了「商用级」，π_Q 取 2.0，结果可能偏高 |
| 怎么消除 | 按客户文件确认档位后，在参数库里把四档改成 SR-332 的 I/II/III 真实因子 |

### 2.3 环境因子

九档（GB 机房 / GF 移动 / GM 便携 / MP 车载 / NS 舰船 / AIC 机载有控 / ARW 机载无人 / SF 航天 / C 恒温机房），档位是简化的，与 SR-332 第 9 章原表不是一一对应。

选择经验：**机房内置设备选 GB；机柜外、车间、户外要往上调一档。** 户外不受控环境在 Issue 4 里已从 1.5 下调到 1.2，如果你们沿用老模板的 1.5，会偏保守。

### 2.4 降额规则

| 项 | 现状 |
|---|---|
| 来源 | 参考 GJB/Z 35-93、IPC-9592 及厂商应用手册的常用档位 |
| 现状 | **示例档位**，26 条规则。军品、车规、消费电子的降额要求差异很大 |
| 后果 | 「超限」和「满足」的判定可能与本单位规范不一致，尤其边界值 |
| 怎么消除 | 用本单位降额规范替换 `derating_v1.json`，JSON 驱动，不改代码 |

### 2.5 磨损件参数

| 项 | 现状 | 影响 |
|---|---|---|
| 电解电容额定寿命/温度 | 示例默认值 | 缺料号 datasheet 时走保守默认（额定寿命取短、温度取低），结果**偏悲观** |
| 风扇 L10 | 示例默认值 | 同上 |
| 日动作次数（继电器/开关/连接器） | 默认 0.002~0.01 次/日 | **对结果极其敏感**：同一个 10 万次继电器，60 次/日算 4.6 年，200 次/日算 1.4 年。必须按实际使用场景填 |
| 日通电时长 | 默认值 | 所有寿命按通电小时算，间断工作的设备日历年限会长得多 |

**这类参数必须由使用场景给出，默认值只够跑通流程。** 报告里应把它列为「关键假设」。

## 三、模型层面的限制

### 3.1 只实现 Method I

| 方法 | 需要什么 | 本系统 |
|---|---|---|
| Method I 零件计数 | 只要 BOM | 支持，且做了应力细化（补 π_V / π_S / 温升） |
| Method II | 实验室试验数据（HTOL、环境应力筛选） | **未实现** |
| Method III | 现场失效数据（RMA / 售后返修） | **未实现** |

后果：报出的失效率缺少实测数据的贝叶斯修正，无法随产品实际表现收敛。

补充说明两点，避免误解：

- **不是做不了，是没有数据入口**。Method II/III 的算法本身不复杂（贝叶斯更新），难点在把返修记录整理成「型号 × 批次 × 通电小时 × 失效数」的结构化格式。部门一旦有 RMA 数据，这块是可以补的，代码里的置信度系数、老化因子都留着开关。
- **业界很多公司名义上有 Method III，实际交的还是 Method I 的数**。现场数据统计口径混乱（退货和返修分不清、批次对不上）是普遍现象，不必因此觉得自己落后。

### 3.2 置信度与老化因子

| 项 | 现状 | 影响方向 |
|---|---|---|
| 90% 置信上限 | 系数取 **1.0**，未做统计修正 | 报出的数字本质是**中值估计**，比标准要求的「90% UCL」偏低，**偏乐观**。客户若要求「按 SR-332 报 90% 置信上限」，这个数不满足 |
| 老化因子（π_CV / 学习曲线） | **关闭**，乘 1.0 | 偏保守。早期缺陷退场后失效率会下降，忽略它意味着长期预测偏高 |

### 3.3 RBD 忽略共因失效

只支持**串联**和**并联（冗余）**两种拓扑。没有 k-out-of-n、没有桥式、**没有共因失效（CCF）**。

后果：并联冗余的收益被高估。两颗器件并联算出来失效率减半，但一次浪涌、一处过热、一个共同的电源轨，可能同时打坏两颗。**这个数字是收益上限，不是期望值。** 界面和报告里已强制提示。

### 3.4 没有热计算

结温 = **环境温度 + 温升**。温升要么用户填，要么用该类别的默认常量。

- 没有热阻 Rθja、没有热仿真、没有功耗推算
- 默认温升与实际发热无关，可能与真实结温差 10~20℃，经 Arrhenius 放大后误差不小
- 想算准，必须补每颗器件的实际温升（界面里可以逐行填）

### 3.5 磨损寿命与 MTBF 不能相加

MTBF 建立在**恒定失效率、指数分布**假设上，它回答「多久坏一次」，不回答「能用多久」。磨损机理（电解液干涸、触点烧蚀、轴承润滑脂耗尽）不服从指数分布。

系统用 **整机寿命 = min(随机失效寿命, 最短磨损寿命)** 来合并，这是工程近似，不是概率推导。看到「MTBF 300 万小时，但继电器 4.57 年」不是矛盾，是两件事。

### 3.6 非电子件不是标准覆盖

螺丝、支架、外壳、线缆、包材这类零件，MIL-217F 和 SR-332 都**没有对应模型**。系统按经验量级（0.01~2 FIT/件）计入，标记 `is_standard=false`，并在结果页与报告里单列告警。

- 计入而非跳过，是**保守方向**（宁可高估失效率）
- 但这批数字**不能作为定稿依据**，更接近「占位值」
- 该做的正确做法是走 NSWC-11 / NPRD，不在 MIL-217 体系内解决

### 3.7 分类引擎不是语义理解

关键词 + IDF 覆盖率 + 字符 n-gram + 位号前缀，四路打分融合。不是大模型，不理解语义。

| 现象 | 说明 |
|---|---|
| 自动归类率约 93% | 剩下 7% 需要人工确认，这是设计意图，不是缺陷 |
| 描述含糊的必然进人工 | 「电容 0.1uF 50V 0603」天生分不出介质，任何规则引擎都分不出 |
| 生僻品类会落到「未识别」 | 下拉框不会预填瞎猜的候选，需要人主动选，选完可沉淀为关键词 |
| 位号只是加分项 | 只能辅助定大类，定不了小类，描述证据强时翻不了案 |

## 四、那它到底哪里有用

限制说完了，说用处。核心一句：

> **绝对值的可信度低，相对比较的可信度高。**

系统误差（λ 基准偏差、质量等级映射）在两份设计比较时会大部分抵消。所以：

| 用法 | 可信度 | 说明 |
|---|---|---|
| 两个方案选型比较 | **高** | 同一套参数下，A 的 MTBF 比 B 高 30%，这个排序基本可信 |
| 找短板 / Pareto | **高** | 哪个器件贡献 80% 失效率，这个结论对参数偏差不敏感 |
| 降额违规初筛 | **中高** | 超限项要人工核对规范，但「有 8 项接近或超限」这个信号很可靠 |
| 磨损件是否成为限制项 | **中** | 数量级判断可信（4 年 vs 10 年），精确值不可信 |
| 对外报 MTBF 绝对值 | **低** | 不可用 |

还有一块经常被低估的价值：**把假设摆到台面上**。以前那张 Excel 里，温升是拍脑袋填的，没人知道。现在每一行都留追溯链——用了什么温升、哪些是默认值、命中哪条规则。设计评审时被问「这个数怎么来的」，能一条条翻出来。

## 五、想提升可信度，按这个顺序做

1. **替换参数库**（成本最低、收益最大）
   用部门手上的标准正本填 `backend/params/mil217f_v1.json`、`telcordia_sr332_v1.json`、`derating_v1.json`。
   只改 JSON，不改代码。改完后的评估用新参数，历史报告的数字不变（结果快照 + param_version）。

2. **补真实工况**
   逐行填实际温升、工作电压/功率、日动作次数、日通电时长。
   这一步不需要任何外部资料，只需要问硬件工程师。做完之后误差通常能收敛一个量级。

3. **对齐报告模板**
   把客户/部门要求的 MTBF 报告格式固化成导出模板，注明假设、参数版本、标准出处。

4. **沉淀 RMA 数据**（长期）
   有了「型号 × 批次 × 通电小时 × 失效数」，Method III 就能接上，那时数字才开始有统计意义。

## 六、部署与安全边界

| 项 | 现状 | 要求 |
|---|---|---|
| 部署形态 | 单机，SQLite，`127.0.0.1` | **只在内网/本机使用，不要暴露到公网** |
| 传输 | HTTP | 无 HTTPS。跨网段访问需自行加反向代理和证书 |
| 账号 | 演示账号（admin） | 多人使用前必须改密码，按人开账号 |
| 并发 | 单进程 | 适合 1~3 人同时用；多人高频使用需换 PostgreSQL + 多 worker |
| 数据备份 | 手动 | 定期复制 `backend/data/reliability.db`；评估结论已存快照，DB 丢了好在参数和结果还能重算 |

## 附：每条限制在系统里哪里能看到

| 限制 | 界面位置 |
|---|---|
| λ 示例值、标准出处 | 左侧「参数库」页，每个标准的 `disclaimer` / `source_ref` |

| 非电子件告警 | 结果页顶部告警条、报告首页「局限性说明」 |

**一句话收尾**：这系统现在的定位是把「拍脑袋的 Excel」换成「假设可见、算法可查、结果可复现的内部估算」。要对外交付，得先过 §5 的第 1 步和第 3 步。
