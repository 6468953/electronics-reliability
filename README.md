# 电子零件可靠性评估系统

一张 BOM 进去，一份可靠性报告出来。中间做四件事：给零件归类、按标准算失效率、算磨损寿命、查降额余量。两套标准可选，MIL-HDBK-217F 和 Telcordia SR-332。

部门内部工具。参数库现在装的是按公开标准整理的典型值，能跑通全流程、能演示方法，**不能拿去签认证报告**。这条边界不写在代码注释里，写在 [docs/02-使用边界与限制说明.md](docs/02-使用边界与限制说明.md)，用之前花十分钟看一遍。

## 跑起来

Windows 双击 `start.bat`，mac/Linux 执行 `./start.sh`。脚本负责建虚拟环境、装依赖、建库、灌一份演示 BOM、找空闲端口、开浏览器。第一次一两分钟，之后几秒。

## 数是怎么算出来的

**失效率**。计数法只要"每类用几只"，不需要电压电流：

```
MIL-HDBK-217F        λ = Σ N × λ_g × π_Q
Telcordia SR-332     λ = Σ N × λ_G × π_E × π_T × π_Q      (π_S 缺省 1.0)
```

单位 FIT，即每 10⁹ 小时一次失效。两套标准写法像，口径差得远：

- MIL 的计数法**不含温度项**，标准原文就这么定义的，它假设器件在典型条件（约 40°C）。界面上把温度从 25 调到 70 而 MTBF 不动，不是 bug。要看温度影响，切应力法。
- Telcordia 的 Method I 自带 π_T，Arrhenius 模型，40°C 为基准，Ea 默认 0.35 eV。

MTBF = 1e9 / ΣFIT。存活率 R(t) = exp(−t/MTBF)，其中 t 是**通电小时**（年限 × 365 × 每天通电小时），不是日历小时。这条最容易算错。

**磨损**。10 个机理各有经验公式：铝电解电容、薄膜电容、风扇、继电器、开关、板对板连接器、线对线连接器、端子、LED、电源模块。以电解电容为例，`L = L0 × 2^((T_rated − T_op)/10) × K_V`，温度每降 10℃ 寿命翻倍，再按工作电压对额定电压的比值打折。

整机寿命取 `min(随机失效年限, 最短磨损件年限)`。这个取小的动作是整个系统最实用的地方：继电器触点磨完那天，MTBF 还有两百万小时也没用。

**降额**。26 类元件各一条规则，判定分四档：满足、接近上限、超限、缺数据。缺数据单列，不当满足。

## 六个设计判断

### 参数放 JSON，不写在代码里

`backend/params/` 下六个文件：两个标准库、降额规则、磨损模型、分类词表、术语表。改 λb 的人不该需要会 Python，参数变更也不该混进代码 diff 里看不清。附带好处是参数能单独版本化，评估记录里存 `param_version`，三年后能还原当时用的是哪版数。

### 计算核心不认识 Web 框架

`backend/core/` 只依赖 dataclass，不 import FastAPI、不碰 ORM，门面是 `core/calc.py::evaluate()`。这样 pytest 能直接对手算结果写断言，也能脱离 Web 跑批处理。公式和数据库一旦缠在一起，两件事都做不了，往后也没人答得上"这个数怎么来的"。

### 分类打分，够不着就不猜

BOM 描述极不规范，`电容 0.1uF 50V 0603` 这种不含品类信息的写法很常见。评分是四路信号：

```
0.50 × 关键词命中 + 0.30 × IDF 加权覆盖率 + 0.20 × 字符 n-gram
再加 位号前缀（仅当候选已有 ≥0.10 分时 +0.10）
```

位号是最可靠的一路：描述可以含糊，`C12` 一定是电容。但它只定大类，陶瓷还是铝电解还得看描述，所以是加分不是判决。

0.70 以上自动归；0.30 到 0.70 进人工队列，给 Top3 候选和各自分数；0.30 以下标未识别，前端不预填任何猜测。Top1 与 Top2 分差小于 0.05 也降级到人工，因为这时候它自己也没把握。

未识别的行不进计算。宁可卡住让人确认，也不猜一个塞进去。

### 标准没覆盖的零件，照样算进去

螺丝、支架、外壳、线束、导热垫、包材，MIL-217F 和 SR-332 都没有模型，业界做法是另配 NSWC-11 或 NPRD，不是硬塞进 217。

系统给这类件标 `is_standard=false`，按 0.01~2 FIT/件 的工程假设值保守计入，并在结果页和报告里点名：有 N 行、M 件属于标准未覆盖件，不能作为定稿依据。

为什么不跳过：跳过会让 MTBF 凭空变好。在可靠性计算里这比参数不准危险得多。

### 缺数据单列一档

不少同类工具把"读不到额定值"当"满足降额"。这里分四档，`no_data` 单独一档，报告给完整清单。同一个原则贯穿全局：缺数据时往保守方向倒，并且说出来。

### 每次评估存快照

一条评估记录存 `assumptions_json + result_json + param_version + engine_version`。参数库以后升级，历史报告的数不会跟着变。报告要能归档，这是前提。

现在这四个数值库里装的都是按公开标准整理的数，每个库的 `data_quality` 标成 `demo`，参数库页、结果页、报告附录三处都会显示。这是刻意留的标记，不是忘了改。

要把数做准：

```bash
python tools/param_worksheet.py export --standard MIL-217F --out 工单.xlsx
python tools/param_worksheet.py import --file 工单.xlsx            # 只校验
python tools/param_worksheet.py import --file 工单.xlsx --apply    # 回写，自动留 .bak
```

回写时按覆盖率把 `data_quality` 从 `demo` 升到 `partial` 或 `verified`，成色标签和报告局限页跟着变。详细步骤见 [docs/03-参数录入指南.md](docs/03-参数录入指南.md)。

MIL-217F 免费，先做这一半。SR-332 买不到授权的话，Telcordia 那条链路只能停在演示水平，这不是代码问题，是数据授权问题。

## 已知限制

- 参数库是整理值，没和原表逐条核对。`lambda_g` 需要按项目实际器件族再校准。
- 分类遇到"纯规格无型号"的描述会落到待确认，这是有意的。
- 磨损只覆盖那 10 个机理。焊点热疲劳、PCB 翘曲、非风扇类轴承都没有。
- Method II（实验室数据）和 Method III（现场数据）没实现。置信度系数、老化因子的字段和开关留着，数据入口没做，因为这两条路的前提是公司真的有实测数据在收集。
- 没有并发编辑锁、审批流、PLM/ERP 接口。
- 分类的打分逻辑前后端各有一份（TS 和 Python），改一边要记得同步另一边。

实现过程中的偏差和踩过的坑记在 [docs/01-架构设计.md](docs/01-架构设计.md) 第 14 节，比前面几节准。

## 打包给别的机器

`pack.bat`，或者 `python tools/pack.py`，产物在 `发布包/`。加 `--with-wheels` 把依赖一起带走（约 38 MB），目标机器只要有 Python 就能离线跑，不需要 Node.js。加 `--with-db` 连当前数据库一起带。

运行期不需要 Node，因为页面已经构建成静态文件由后端托管。
