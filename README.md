# 电子零件可靠性评估系统

把「一张 BOM」变成「一份能签字的可靠性报告」的 Web 系统：BOM 导入 → 自动分类 → 人工确认 →
可靠性预计（MIL-217F / Telcordia SR-332 双标准）→ 磨损寿命 → 降额检查 → 敏感性分析 → PDF/Excel 报告。

> ⚠️ **重要声明**：本系统内置的参数库是按公开标准的典型值整理的**示例数据**，用于演示与教学，
> **不得作为产品认证、招标应答或安全定级的依据**。真实项目请以正版标准原文表格、厂家 datasheet
> 与本单位历史失效数据替换 `backend/params/*.json`。

## 一、怎么启动

### 方式 A：一键启动（日常使用就用这个）

**Windows：双击 `start.bat`**　　**macOS / Linux：`./start.sh`**

脚本会自动完成：检查页面 → 找/建 Python 环境 → 装依赖 → 挑空闲端口 → 起服务 → 打开浏览器。
启动后看这个窗口：

```
 ------------------------------------------------------------
   界面地址：  http://127.0.0.1:8000
   接口文档：  http://127.0.0.1:8000/docs
   演示账号：  admin / admin123
 ------------------------------------------------------------
```

### 图形界面到底在哪？

**在浏览器里，是一个网页（HTML + JS）。** 不是桌面软件，也没有 `.exe`。

- 那个黑底命令行窗口 = **服务进程本身**，关掉它（或 Ctrl+C）服务就停。
- 页面文件在 `frontend/dist/`（`npm run build` 的产物），由后端顺带托管，所以
  **只需要一个端口、一个进程**，不用装 nginx。
- 想把界面钉在桌面上：右键 `start.bat` → 发送到 → 桌面快捷方式，双击即可。

### 方式 B：开发模式（要改代码时才需要）

需要 Python 3.10+ 与 Node.js 18+。

```bash
# 1) 后端（首次启动会自动建库、建账号、建知识库、灌一份演示 BOM）
cd backend
python -m venv .venv
source .venv/Scripts/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
# 接口文档：http://127.0.0.1:8000/docs

# 2) 前端（另开一个终端，带热更新）
cd frontend
npm install
npm run dev
# 打开 http://127.0.0.1:5173
```

> 两种方式的区别只有一个：开发模式的页面在 5173（Vite 热更新，改代码立即生效）；
> 一键启动的页面在 8000（已构建的静态文件，改代码要重新 `npm run build`）。
> 后端 API 是同一套。

演示账号（首次启动自动创建）：

| 账号 | 密码 | 权限 |
| --- | --- | --- |
| `admin` | `admin123` | 管理员：可维护分类知识库、关键词、查看操作日志 |
| `engineer` | `engineer123` | 工程师：只能看到自己的项目，不能改知识库 |

> 数据库默认落在 `backend/data/reliability.db`（SQLite）。想重置演示数据就删掉它，下次启动会重新生成。

## 三、技术栈与选型理由

| 层 | 选型 | 为什么 |
| --- | --- | --- |
| 后端 | **Python 3.13 + FastAPI** | 计算核心是纯函数库（`backend/core/`），与 Web 层完全解耦，可被 pytest 与 CLI 单独调用。Python 在数值/公式表达上比 Node.js 简洁，且 `jieba`（中文分词）只有 Python 生态有成熟实现 |
| 前端 | **React 18 + TypeScript + Vite + Ant Design 5 + ECharts 5** | 表格/表单密集型后台，AntD 能省掉一半以上样式代码；ECharts 的 Pareto、双轴、markLine 直接可用 |
| 数据层 | **SQLAlchemy 2.0 + SQLite**，可切 PostgreSQL | 演示零配置；`DATABASE_URL` 一改即迁移，代码无方言依赖（只用了关系与索引） |
| 认证 | **JWT（PyJWT）+ PBKDF2** | 无会话状态、免 Redis；密码用标准库 `hashlib.pbkdf2_hmac`（260k 轮），不引第三方 |
| 报告 | **reportlab（PDF）+ openpyxl（Excel）** | PDF 需精确控制分页与中文字体（注册 `msyh.ttc`）；Excel 需多 sheet 与列宽 |

**为什么"计算核心与 Web 层解耦"是硬要求**：公式一旦和 ORM 混在一起，就没法写单元测试、没法复现历史结果、
也没法回答"这个数怎么来的"。现在 `core/` 只认 dataclass（`PartInput` / `Assumption` / `ParamSet`），
换框架、换数据库、跑 CLI 都不影响公式。

## 五、几条关键计算口径（评审最常问的）

1. **λ = λb × πQ × πE**（计数法）／**再乘 πT × πV/πS**（应力法）。
   `FIT = 每 10⁹ 小时的失效次数`，`MTBF = 1e9 / ΣFIT`，`R(t) = e^(−t/MTBF)`，
   其中 `t = 目标年限 × 365 × 日通电小时`（**不是日历小时**，这一点最容易算错）。
2. **判定 PASS 需同时满足**：目标年份存活率 ≥ 目标值；若填了 MTBF 门槛，还需 MTBF ≥ 门槛。
3. **计数法不含温度项**（MIL 的口径就是如此），所以 40°C 与 70°C 的计数法结果相同。
   这不是 bug：`πT` 只在应力法与 Telcordia 里出现。系统的敏感性页会主动说明这一点。
4. **磨损与随机失效是两条竞争路径**，整机结论 = `min(随机视角年限, 最短磨损件年限)`。
   页面与报告刻意不写"本品寿命 X 年"，只写"某机理预计 X 年后失效"。
5. **并联冗余的收益是上限**：按"共因失效可忽略"计算，系统会强制提示这一点。
   只有 1 个成员的冗余组会自动退化为串联（单件冗余没有收益）。
6. **降额分四档**，其中 **`no_data` 单列一档**：很多工具把"缺数据"当"满足"，本系统不这么干，
   报告里会明确给出"39 项无法判定"的清单。
7. **评估是快照**：`assumptions_json + result_json + param_version + engine_version` 全存。
   参数库以后升级，旧报告的数字也不会变——这是报告能归档的前提。

## 六、参数与假设的边界

- 环境倍率、质量因子、类别 λb 均为**示例值**，来源写在 `params/*.json` 的 `source_ref` 字段里，
  界面上「参数库与来源」页可直接查看。
- 系统有 15 条明确的工程假设（A1–A15，见 `docs/01-架构设计.md`），例如：
  默认环境类别取 GB、默认商用级器件、忽略共因失效、磨损件只算 8 类机理、焊点按 1 个大类计数等。
- **缺数据时的处理一律偏保守**（宁可报低让人核实，也不报高让人误判），并在结果页与报告里标注。

## 八、整包迁移与离线部署

### 三种"搬走"的方式

| 场景 | 做法 | 包大小 | 目标机器需要 |
| --- | --- | --- | --- |
| 换目录 / 换盘 | 整个文件夹剪切过去 | 约 1 MB | 无（依赖已在 .venv 里） |
| 给同事、换台机器 | 双击 `pack.bat` | 约 1 MB | Python 3.10+，首次启动联网装依赖 |
| 内网、无外网 | `pack.bat --with-wheels` | 约 38 MB | 只有 Python 3.10+，全程离线 |

> 第一行「整个文件夹」= 当前项目根目录，含 `backend/.venv` 与 `frontend/dist`。
> 它只有在本机、同 Python 版本时能直接跑；跨机器建议用发布包。

### 打包

双击 `pack.bat`，或命令行：

```bash
python tools/pack.py                  # 普通包（目标机器联网装依赖）
python tools/pack.py --with-wheels    # 连依赖一起带，完全离线
python tools/pack.py --with-db        # 连当前数据库一起带走（保留已录入的项目）
```

产物：`发布包/可靠性评估系统-v1.0/`（目录）和同名 `.zip`（发给别人用这个）。

### 发布包里有什么、没什么

**有**：`backend/` 源码与参数库、`frontend/dist`（已构建好的页面）、`docs/`、`start.bat`、`start.sh`、
`tools/wait_and_open.py`、`README.md`、（可选）`wheels/`、空的 `backend/data/`。

**没有**：`.venv`（370 MB）、`node_modules`（263 MB）。这两个目录里塞满了与当前机器、
当前 Python 版本绑定的绝对路径，拷到别处大概率跑不起来，还白白多背 630 MB。

**也没有 `frontend/src` 和 `frontend/index.html`**。发布包的定位是"拿来就跑的运行版"，
只需要构建好的 `dist`；`frontend/index.html` 是 Vite 的源模板（里面写的是
`<script src="/src/main.tsx">`），长得像"双击这个就能打开系统"，但双击只会得到白屏或
一句 `Failed to fetch`，是个纯粹的诱饵文件。要改前端请在源码仓库里改，`npm run build` 后重新打包。

### 为什么运行期不需要 Node.js

页面已经 `npm run build` 成静态文件（`frontend/dist`），由后端在根路径托管。
Node 只在"要改前端代码"时才需要。

### 离线安装踩过的坑（已修）

`jieba` 只发布源码包，安装时要现场编译；而 **Python 3.12 起 `venv` 不再自带 setuptools**，
于是在无网机器上 `pip install --no-index` 会直接失败：

```
ERROR: Could not find a version that satisfies the requirement setuptools>=40.8.0 (from versions: none)
```

现在 `pack.py --with-wheels` 会用 `pip wheel` 把源码包**预先编译成 whl**（编译发生在有网的打包机上），
并额外带上 `setuptools` / `wheel` 兜底，保证目标机器只解压、不编译。

### 开放给局域网其他人访问

默认只监听 `127.0.0.1`（只有本机能访问）。要让同事用内网地址访问：

```bash
backend/.venv/Scripts/python.exe -m uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port 8000
```

别人访问 `http://<你的内网IP>:8000` 即可。这种情况是**同源**访问，不需要动 CORS。

如果前后端分开部署（前端另用 nginx），用环境变量指定白名单：

```bash
CORS_ORIGINS="http://10.0.0.8:5173,https://rel.example.com"
```

### 迁移后要注意的两件事

1. **报告文件路径**：`reports` 表里存的是生成时的绝对路径。换机器后旧 PDF 的"下载"会失效，
   但可以重新生成 —— 评估记录与参数快照都在库里，重算出来的数字完全一致。
2. **PDF 中文字体**：按 msyh → simhei → simsun → PingFang → 文泉驿 → Noto 的顺序找系统字体。
   Linux 服务器上一个都没装的话，PDF 中文会退化成方块并在日志里给警告，装个 `fonts-noto-cjk` 即可。

## 十、常见问题

**Q：页面能打开，但点任何按钮都报 `Failed to fetch` / 「连不上后端服务」？**
这是最常见的一条，几乎都出在"页面还在、服务没了"。按顺序看：

1. **启动服务的黑色窗口是不是被关掉了？** 那个窗口就是服务本体，关掉窗口 = 关掉服务。
   浏览器里已经加载好的页面仍然能点，但每个请求都发不出去。重新双击 `start.bat`，然后刷新页面。
2. **地址栏端口和服务端口是否一致？** 8000 被占用时脚本会自动顺延到 8001~8010，
   窗口里会打印 `[!] 8000 端口被占用，自动改用 8001`。别用旧的地址。
3. **是不是双击了 `frontend/dist/index.html`？** 那样地址栏是 `file:///...`，同源策略下
   请求一律失败。正确做法永远是双击根目录的 `start.bat`。
4. 电脑刚从睡眠恢复时，本地服务的连接可能已失效，重启 `start.bat` 即可。

页面顶部会出现一条红色横幅，把"连接已断开 + 怎么恢复"直接写出来，右侧有「重新检测」按钮
（15 秒也会自动复查一次）。所以正常情况下不需要靠猜。

**Q：温度敏感性曲线是平的？**
计数法不含温度项，属正常。改用「零件应力法」或切换到 Telcordia SR-332 即可看到斜率。

**Q：为什么评估按钮点不动 / 报"还有 N 行未完成分类"？**
待确认与未识别的行不会进入计算（避免把猜错的分类静默算进去）。先去 ② 页把这 7 行确认掉。

**Q：降额里"缺数据"是不是可以忽略？**
不可以。它表示"额定值或工作应力读不到，无法判定"，报告里会单列清单。
处理方式：在 ① 页补录该行的额定值/应力，或把描述写清楚（如 `CAP ALU 100uF 63V 105℃ 2000h`），然后重新评估。

**Q：PDF 中文变成方块？**
系统会尝试注册 `C:/Windows/Fonts/msyh.ttc`（Windows）或 `NotoSansCJK`（Linux）。找不到时会在报告首页
显式打印警告，而不是静默输出方块。安装任一中文字体后重新生成即可。

**Q：报表里的数字和三个月前不一样？**
如果不一样，先看两边的 `param_version`。参数库升级会产生新的版本号；同一份评估记录的数字不会变。

## 十点五、开发期自检脚本

前端带两个基于 `playwright-core`（不下载浏览器，直接用本机 Chrome）的冒烟脚本，
能在真实浏览器里抓 React 运行时错误——这是类型检查与构建抓不到的：

```bash
# 先启动后端 8000 与前端 5173
cd frontend
node scripts/smoke.mjs   # 只逛页面（登录 → 工作台 8 个 Tab → 知识库/术语表/参数库），截图到 shots/
node scripts/flow.mjs    # 完整流程：确认 7 行队列 → 评估 → 结果/追溯/双标准 → 磨损/降额/敏感性/报告
node scripts/diag.mjs    # 三条"用户会踩的路径"：file:// 打开 / 正常使用 / 服务中途断掉
```

`diag.mjs` 专门验证"出错时说的话人能不能看懂"：双击 index.html 应当看到中文说明页而不是白屏；
服务断掉时应当出现中文横幅和「重新检测」按钮，**不应把浏览器原生的 `Failed to fetch` 漏到界面上**。
这三条断言写死在脚本里，改动前端错误处理时跑一遍就知道有没有退化。

两个脚本都会把 `console.error` 与 `pageerror` 汇总打印，退出码为 1 表示有报错。
`flow.mjs` 会写数据库，跑完想恢复初始状态：删掉 `backend/data/reliability.db` 再重启后端即可。

## 十一、已知限制

- 参数库是示例值，未做与正版标准的逐条核对；λb 的取用需要按项目的实际器件族再校准。
- 分类引擎对"纯规格无型号"的描述（如 `电容 0.1uF 50V 0603`）会落到待确认——这是有意的保守设计。
- 磨损模型只覆盖 8 类机理，未含轴承（非风扇）、继电器机械寿命、焊点热疲劳、PCB 翘曲等。
- 未实现：多用户并发编辑锁、审批流、与 PLM/ERP 的接口、批量项目的横向看板。
